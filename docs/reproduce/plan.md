# Free-compute reproducibility test: plan

Status as of 2026-11-11. Reviewed with Claude Fable 5.2 agents.

## What it is for
Anyone should be able to check this project's numbers without the owner's laptop. The script `scripts/reproduce.py` rebuilds part of Hurricane Ian from NASA Black Marble night-light images and the EAGLE-I outage counts, then compares the result with what the repository committed. It is meant to run on a laptop, on Google Colab and on GitHub Actions. It prints one line per check, marked PASS or FAIL, and rewrites a JSON report (the `--report` file) after every check. Its last line is the verdict: PASS when the run reached its end and every check passed, FAIL otherwise (an unexpected error is recorded as a failed check named "run aborted"). A run that is killed or interrupted prints no verdict. Its report says `"complete": false`, and the notebook and the GitHub run summary show it as INCOMPLETE, or as FAIL when a check had already failed.

| 2 | Does level 0 first. Every size in the table is an estimate taken from the README and the workflow file, and so is the time of level 0. The times of levels 1 and 2 were measured. On GitHub Actions each was measured twice, from start to finish, on 2026-11-10 in the development repository and on 2026-11-11 (US Pacific time) in the public one: level 1 about 3 minutes both times, level 2 about 4.5 minutes and about 5 minutes. On Colab each was measured once, on 2026-11-11 (US Pacific time), from the start of the run to the printed verdict: level 1 about 4.5 minutes in a new session, then level 2 about 5.5 minutes in the same session. That session still held the EAGLE-I, Census and HURDAT2 files and the installed Python packages from the level 1 run, so the level 2 time leaves out the start of a session and about a minute of downloading and installing that the level 1 time includes. Before these runs the README, the notebook and the script gave estimates for Colab (15 to 25 and 35 to 60 minutes) that proved several times too long; they now give the measured times. Downloads are smaller on a machine that already holds some of the files. Also measured so far: level 0 in about half a minute on the local Mac and in under 1 minute on GitHub Actions (one run, in the public repository), and, on the local Mac only, the full Ian build in about 8 minutes when the table behind the fingerprint was built. Level 0 runs the test suite without the 7 tests in `tests/realdata`, so it reports 7 fewer tests than a full run of the suite. The token is the free NASA Earthdata token. Before anything large is downloaded, levels 1 and 2 try the token on one byte of a real satellite file. They then check the EAGLE-I, Census and HURDAT2 downloads against the checksums and the row count written down in `docs/reproduce/inputs.json` (this is called pinning), and they start the rebuild only if every check so far has passed. A full run makes 3 checks at level 0 and 10 at level 1 or 2.

## Where it runs
- **Laptop:** in the repository folder, run `uv sync` once, then `uv run python -I scripts/reproduce.py --level 1 --report reproduce-report.json` (use 0 or 2 for the other levels). The token is read from the `EARTHDATA_TOKEN` environment variable or from a `.env` file in that folder. Rebuilt tables go to a temporary folder that is removed afterwards. Nothing in `data/processed` is touched.
- **Google Colab:** go to colab.research.google.com/github, search for `mukuna-web/blackout-from-space` and open `notebooks/reproduce_colab.ipynb` (only for a private copy: first tick the box that includes private repositories). Choose LEVEL in cell 1 (it starts at 1) and run the four code cells from top to bottom. Keep the tab open until cell 4 prints the verdict: the README warns that free Colab ends the session on disconnect and keeps nothing.
- **GitHub Actions:** on the repository page choose Actions > reproduce > Run workflow, pick the level (it starts at 1) and press Run workflow. GitHub offers Run workflow only to accounts with write access, so an outside reader runs it in a fork of their own (one-time setup, step 3). The report is attached to the run as a download named `reproduce-report` (kept 30 days) and summarised on the run page. If the secret `EARTHDATA_TOKEN` is missing, a level 1 or 2 run stops with an error before the script starts: nothing is rebuilt and no report is attached. Only a fork (a copy of the repository under another account) drops to level 0, with a warning. The workflow stops a run after 2 hours, or 4 hours for level 2.

## One-time setup for whoever runs it
1. Make a free NASA Earthdata token: log in at urs.earthdata.nasa.gov and choose Generate Token on the profile page.
2. Add it in Colab: click the key icon in the left bar (Secrets), add a secret named `EARTHDATA_TOKEN` with the token as its value, and allow the notebook to read it.
3. Add it on GitHub: in the repository choose Settings > Secrets and variables > Actions > New repository secret, type the name `EARTHDATA_TOKEN`, paste the token and press Add secret. The development repository (the private one the project was built in: README, project notes) got its secret on 2026-11-10, and the public repository got its own on 2026-11-11. An outside reader does the same in a fork of their own, after enabling Actions there if GitHub asks.
4. Only if you keep a private copy: also make a read-only GitHub token (profile picture > Settings > Developer settings > Personal access tokens > Fine-grained tokens > Generate new token; choose Only select repositories and the copy; under Permissions set Contents to Read-only). Add it in Colab as the secret `GITHUB_TOKEN` and set REPO in cell 1 to the copy. Colab then needs it at every level, and only to download the code. The public repository needs no GitHub token.
5. Earthdata tokens expire 60 days after they are generated. The token check at the start of a run says when the token is rejected. Then make a new one and replace it in Colab, on GitHub and in the laptop's `.env` file. The menu names in steps 1 to 4, and the Colab page named under Where it runs, are the websites' own, as known when this plan was written: nothing in the repository can check them.

## What a pass means, and what it does not
- **Level 1 pass:** the pipeline, run from scratch on another machine, gives the same table as the committed sample. All 23 columns of all 165 rows match: names and labels exactly, pass times to the second, and numbers within small rounding tolerances (counts of customers and housing units exactly).
- **Level 2 pass:** the rebuilt table for all of Ian matches the committed fingerprint, which holds counts and sums for each night and each county, plus Lee County's full series. It also holds how many values each summed column has, for each night and each county (`present_per_night` and `present_per_county` in the file), because a sum cannot tell a missing value from a zero. A fingerprint is a summary, not the table: a rearrangement that keeps every one of those sums and counts would not be noticed.
- **A satellite file that cannot be read fails the run.** It is listed under the check "satellite downloads", which fails, and under `build` in the report. The tables are then not compared: the comparison line reads "not compared" and counts as failed too. This is a failed download, not a different number, so the remedy is to run again. A file missing from NASA's listing is reported the same way.
- **Only a finished run can pass.** A run that was killed or interrupted leaves a report with `"complete": false` and `"passed": false`. The notebook shows it as INCOMPLETE, and so does the GitHub run summary when one could still be written.
- **A pass does not re-run the lockbox test** (the one-time test on the two storms that were kept locked away, Helene and Milton). The lockbox result is frozen in `docs/lockbox_result.json`. Level 0 checks that file against the SHA-256 checksum stored in `docs/lockbox_record.json` and never recomputes it. The frozen verdict is "fail", and a pass here does not change it.
- **A pass does not cover the other storms or recompute the scorecard.** Only Hurricane Ian is rebuilt. A pass shows that the numbers can be rebuilt, not that the model's estimates are right.

## What the review found
Round 1 (2026-11-09 to 2026-11-10). Four reviewers, one for each angle (compare, colab, actions, inputs), reported 24 findings. A separate skeptic tried to refute each one and refuted none: 21 were confirmed and 3 confirmed in part. 23 were fixed and 1 is left open (actions-6). The fixes in the script, the notebook and the pipeline came with tests. No test reads the `reproduce` workflow file or the README, so the changes made there (actions-3, actions-4, actions-5, inputs-4) were checked by reading. The ratings in brackets come from the review. Every fix named in this section was found in the files on 2026-11-10.
- Token leak (high: compare-1, colab-2, actions-1, inputs-2; low: compare-6). A token pasted with a stray space or line break was written in full to the log, the notebook output and the uploaded report. An error text was also cut to 300 characters before it was masked, so part of a signed download address could survive. Fixed: the token is trimmed, a malformed one is refused without being shown, whatever follows the word Bearer is masked, and masking comes before every cut.
- False pass (high: compare-2, colab-1, actions-2, inputs-1). The report said `"passed": true` until a check failed, so a killed or cancelled run, or an old report, could read as a pass in the notebook and in the report uploaded by GitHub. Fixed: the report is written as incomplete the moment a run starts, a run passes only when it reaches its end, and the notebook deletes the old report first and prints PASS only for a finished run at the chosen level.
- Gaps in the comparisons (medium: compare-3, compare-5). Level 2 could not tell which county a value belonged to, so a table with values shuffled between counties passed. Level 1 never compared 4 of the 23 columns. Fixed: the fingerprint holds per-county totals of every column, and level 1 compares all 23 columns and wants exactly those columns in both tables.
- Failed satellite downloads (low: compare-4; medium: colab-3, inputs-5). A pass-time file missing from NASA's listing went unreported, and a failed download was also reported as a failed comparison. Fixed: a missing file fails the "satellite downloads" check, and the comparison is then skipped and marked "not compared".
- Colab notebook (low: colab-4, colab-5, colab-6). An empty secret was accepted, an unanswered access prompt could crash the first cell even for a secret the run did not need, and the second cell reused an old copy of the code after the repository or branch setting changed. Fixed: an empty secret counts as missing, the first cell stops with instructions for a needed secret and carries on without an optional one, and the second cell stops and says to delete the old copy.
- Missing secret on GitHub (low: actions-3). Without the secret, a level 1 or 2 request quietly ran level 0 and ended green. Fixed: it stops with an error, and only a fork drops to level 0, with a warning.
- Wording (medium: actions-4, inputs-4; low: actions-5). The workflow text said a failing check names the changed input, called the runner free and gave run times. But NASA's satellite files are not pinned, nothing had been timed, and runs in a private repository are metered. Fixed in the wording only: the limits themselves remain (see Known limits).
- Action versions (low: actions-6). The workflow names its three actions by version tags that can move, not by fixed commit hashes. Not fixed: only the setting `persist-credentials: false`, which keeps the GitHub login out of the checked-out folder, was added.
- EAGLE-I file on disk (medium: inputs-3). A file already on disk was trusted unchecked, so a cut-off file passed. Fixed: a kept file must be readable and hold the pinned 25,796,465 rows, and a new file is written under a temporary name first.
- Missing tests (medium: inputs-6). No test ran the script's main path, the rebuild, the input checks or the EAGLE-I fetch script. Fixed: offline tests for all of them were added.

Later rounds. An independent checker then demonstrated 5 further issues (C1 to C5). The check of their fixes found 3 more, rated low (D1 to D3). All 8 are fixed, each with a test, and the last check round found every fix holding. That round also reported 4 new issues, rated low. Three were closed afterwards by the orchestrator, without a further check round: the `--report` option now refuses a path inside `data/` or `docs/` (with tests), the README and the notebook now mention the counts of present values, and a test that tied this plan's test count to the size of the suite was removed as too brittle. One is still open and is the Known limit marked "last check round".
- C1, D2: one new test file held a line that the repository's own scan for pasted tokens would have flagged once the file was committed. The scan read only files git already tracks, and it passed over any file whose name holds a letter outside the English alphabet, a quote or a line break. Fixed: the line was rewritten, the scan reads new files too and takes their names from git as they are, and a failing scan names the file without showing the token.
- C2: when the repository or branch setting changes, the notebook's second cell asks for the old copy of the code to be deleted. The session was then left inside the deleted folder, where git cannot run. Fixed: the cell first moves back to `/content`.
- C3: outside Lee County, level 2 could not tell a missing value from a zero, because a sum skips missing values. Fixed: for each of the 17 summed columns the fingerprint also counts the values present, for each night and each county.
- C4, D1: the script refuses a `--scratch` folder (the folder a rebuild writes into) inside `data/` or `docs/`, but it compared folder names as text. `DATA/processed` on a disk that ignores upper and lower case got past it, and so did a folder reached through a link. With a scratch folder whose own `interim` folder was a link to the real one, a rebuild would first have deleted the real EAGLE-I extract. Fixed: folders are compared as places on disk and links are followed. No such link exists in this repository today.
- C5: the notebook tests left their made-up token in the `EARTHDATA_TOKEN` environment variable, where the tests that ran after them found it. Fixed: the variable is put back as it was, set or not, and a check fails if a test leaves it changed.
- D3: this plan was out of date. It gave an old test count, did not mention the fingerprint's counts of present values and did not say why level 2 was pending. Fixed, and one test now reads this plan: it checks the level 2 sentence above. The finding also asked for one level 2 run. The fix rounds were not allowed to download from NASA, so that run was made in the final run (see Verification status).

## Known limits
- NASA's satellite files (granules) are not pinned. Each download is checked only against the MD5 checksum NASA lists for it that day. If NASA reprocesses the files, the comparison fails with different numbers and looks the same as a code change: no check reports it as an input change.
- The workflow names its three actions by version tags that can move (`actions/checkout@v4`, `astral-sh/setup-uv@v5`, `actions/upload-artifact@v4`), not by commit hashes (finding actions-6).
- On the first GitHub run of this test (2026-11-10, in the development repository), GitHub warned that those three actions target Node.js 20, which it calls deprecated, and ran them on Node.js 24. The run passed. The public repository's runs of 2026-11-11 (US Pacific time) carry the same warning. Newer versions of the actions will be needed at some point.
- Levels 1 and 2 have each run on Google Colab only once, level 2 only in a session that had just run level 1, and a Colab run leaves no public record that a reader could open. Level 0 has not been run there on its own: its three checks passed as the first three checks of both runs. Apart from those two runs, the timed runs on GitHub (one for level 0, two each for levels 1 and 2) and the times measured on the local Mac, the times and download sizes quoted are estimates. The README's statement that Colab's 12 GB of memory is enough rests on that one level 2 run. GitHub runs are free for a public repository; in a private copy they are metered against the plan's included usage.
- The level-2 fingerprint is a summary. A rearrangement that keeps every night's and every county's totals and counts of present values would pass.
- Last check round (low, open): the `--scratch` guard compares folders, not single files. A link to one real file, placed in the scratch folder under the name of an output, is not noticed, and a rebuild writes through it. The guard also follows links only for the folders the pipeline keeps its files in (`data/processed`, `data/interim`, `data/raw`, `data/sample`, `docs/img`).
- A pass on the local Mac is a weaker test than one on Colab or GitHub. The EAGLE-I, Census and HURDAT2 files are already on its disk, and so are the 110 satellite files of tile h09v06, the one tile level 1 uses. The build reads a local satellite file when its name matches NASA's listing, so a local level 1 may read every satellite file from disk and not test the download at all.
- NHC replaces its dated HURDAT2 file each spring (a note in the script). After that, the HURDAT2 check fails on a fresh machine until a copy of the pinned file is committed or the pin is updated.
